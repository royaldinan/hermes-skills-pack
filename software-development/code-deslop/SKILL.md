# Code De-slop: Remove AI Patterns from Source Code

Identify and remove signs of AI-generated code while preserving correctness and all functionality. The humanizer skill covers prose; this covers source code (comments, naming, structure, idiom choices).

## When to Use

- User asks to remove AI slop, AI-isms, or ChatGPT artifacts from code
- User needs code to look human-written (academic submissions, portfolio, contributions)
- Reviewing code that was generated by an LLM and needs to pass as hand-written
- User says "hilangin unsur AI slop" or equivalent

## Research Basis

The patterns below are grounded in classifier research (arXiv:2607.13077, AUROC 0.996) that found AI-generated code comments concentrate in two categories:
- **Explanation comments**: restate what the next line obviously does
- **Meta comments**: narrate structure the code already provides (section headers, file-level summaries)

Do not invent detection criteria from intuition. When in doubt whether something is AI slop, check: does this comment/pattern add information a competent reader of the code does not already have from reading the code itself?

## Procedure

1. **Read the full source file.** Understand all logic before touching anything.

2. **Identify reference constraints.** If the user says certain code patterns must be preserved (e.g., lecturer's whiteboard code, upstream API style), note them. Never alter preserved reference logic — only strip the slop layer around it.

3. **Audit comments against the research criteria.** For each comment, ask: does this restate the line below it, restate the function signature, or add a structural label the code already provides? If yes, it is slop. Build a mental (or actual) table: location, comment text, verdict.

4. **Identify structural AI tells:**
   - ASCII section-divider banners wrapping functions or blocks (`// ---------`, `// ======`, `# ======`, `# ######`, `/* ****** */`)
   - File-header block comments that narrate what the file does when the code already shows it
   - Numbered section labels (// 1. STRUCT, // 2. INSERTION, etc.)
   - Over-explaining obvious logic in multi-line docstring-style comments above simple functions

5. **Identify naming/idiom tells (language-dependent):**
   - In C/C++: using namespace std + raw new/delete + C-style casts + 0 instead of nullptr — these co-occur disproportionately in LLM output for beginner prompts. But do NOT change these if the user/lecturer requires that style.
   - Overly descriptive variable names that read like prose (studentToDeleteFromList vs target)
   - Function names that embed their return type or full behavior description

6. **Remove slop, preserve useful comments.** Keep comments that explain WHY (non-obvious reasoning), not WHAT (restating code). The test: if you delete the comment, does a competent reader lose information they cannot recover by reading the code? If no, delete it.

7. **Do NOT alter logic, behavior, or functionality.** The refactor is cosmetic + comment-level only unless the user explicitly asks for logic changes.

8. **Compile and test.** Always compile with strict warnings (-Wall -Wextra or equivalent) and run the program with representative inputs covering: normal operation, edge cases (empty input, boundary values), and error paths. Do not claim "it works" without actual execution output.

9. **Verify file persistence.** If the program writes to files, confirm the file reflects the operation after the test run.

## What to Keep vs Remove

### REMOVE (AI slop):
- `// main.cpp` (filename-as-comment)
- `// --------- Helpers ---------` or `// =====================` (section and banner dividers)
- `// Returns true if found` (when signature is `bool Find(...)`)
- `// Reads the file line by line` (above a `while(getline(...))` loop)
- `// Validates the six fields of one record` (above `validateRecord(f[0]..f[5])`)
- Multi-line header blocks narrating the file's purpose, format, and examples
- Comments that restate the if-condition on the next line
- Numbered sequential tutorial steps (`// Step 1: ...`, `// Step 2: ...`)
- Defensive I/O boilerplate and over-engineered fallback cascades with self-narrating print statements (e.g., `print("Loaded dataset from sidebar upload...")`, multi-branch checks for trivial file reading, interactive prompt widgets wrapping standard CLI/notebook reads)
- Comments that narrate runtime environment mechanics or UI instructions (e.g., `# target dataset uploaded to colab sidebar`, `# interactive upload prompt if file not found`)

### KEEP (genuinely useful):
- Shorthand pointer/memory ownership signposts (`// copy before delete`, `// unlink node`)
- Platform-specific workarounds (`// replace existing file` on Windows `rename`)
- Data format / index signposts (`// name, id, gender, batch, smstr, gpa`, `// 1-based index`)
- Non-obvious algorithmic choices (`// sort desc by gpa`)

## Writing Natural, Human-Level Comments (When Comments Are Needed)

Completely stripping all comments can make code look artificially sterilized or bare. When adding comments to humanize code, apply these developer-grade rules:

1. **Ultra-Compact Shorthand Over Full Sentences (CRITICAL)**:
   Programmers do not write grammatically complete, multi-clause academic sentences in code comments. Full sentences with conjunctions (*"otherwise"*, *"in order to"*, semicolons) are an instant giveaway of AI generation. Real human comments are **short signpost fragments (2–5 words, lowercase, no ending period)** that serve as visual bookmarks while scrolling.

   | AI Slop (Verbally Over-Explained) | Real Programmer (Compact Signpost) |
   | :--- | :--- |
   | `// insert sorted by GPA descending; >= keeps arrival order stable` | `// sort desc by gpa` |
   | `// update head if inserting at the front, otherwise link after prev` | `// link node` |
   | `// bypass target node: handle head removal vs middle/tail` | `// unlink node` |
   | `// Windows std::rename fails if destination exists; remove old file first` | `// replace existing file` |
   | `// expected fields: 0=name, 1=id, 2=gender, 3=batch, 4=smstr, 5=gpa` | `// name, id, gender, batch, smstr, gpa` |
   | `// copy id and name before Delete() frees the allocated memory` | `// copy before delete` |
   | `// 1-based index matching the display table row numbers` | `// 1-based index` |

2. **Explain "WHY" as a Shorthand Tag, Never Narrate "WHAT"**:
   - Bad: `// Loop through all nodes in the linked list`
   - Good: `// sort desc by gpa`
3. **Tactical Density**:
   - Sparse density: 5–8 compact signposts across an entire 300+ line file is ideal. Never comment every function or block.
   - Tone: direct, lowercase, shorthand, no emojis, no tutorial voice.

## Pitfalls

- Do not assume all comments are slop. Audit each one individually against the research criteria.
- Avoid replacing AI slop with full-sentence "explanatory" comments that still sound like AI-written documentation. Keep human comments strictly compact (2–5 word fragments).
- Do not change coding style (e.g., replacing 0 with nullptr, or adding const) unless the user asks. The goal is removing AI tells, not modernizing the code.
- When reference code exists (lecturer notes, whiteboard photos), the core algorithm must remain structurally identical — same variable names (cur, prev, temp), same conditions (>=), same branching pattern.
- Vision models often hallucinate handwritten code from whiteboard photos. Cross-reference with the DOCX chat history or user's verbal description. If uncertain, ask.
- The user may have mixed Indonesian and English instructions. The code output should match whatever language the user specified (usually full English for academic submissions).
- Restore test data files to their original state after testing, so the user's data is not left modified.
- Maintain ONE clean canonical filename (`dataset.csv`) as the single source of truth; overwrite the canonical file with updated data rather than creating messy variant copies like `_enriched`, `_v2`, or `(1)`, and avoid writing candidate search lists in code that check for temporary suffix artifacts.
- For Google Colab notebooks, avoid over-engineering file loading with multi-branch fallback cascades, `files.upload()` prompts, and environment-narrating comments/prints. Write a clean 3-line loader: check `os.path.exists(filename)`, download via `urllib.request.urlretrieve(raw_url, filename)` if absent, and read directly with `pd.read_csv(filename)`. This automatically fetches the file into the Colab workspace while respecting any user-uploaded file without verbose ceremony.
- When migrating or replacing Java/Kotlin starter files into an existing Android Studio project, always synchronize the package declaration with the destination project's namespace/folder structure (otherwise R class references fail with 'package R does not exist'), update full-class references in XML layouts (e.g. FragmentContainerView), and declare all new Activity classes in AndroidManifest.xml to prevent runtime ActivityNotFoundException.
- When generating Jupyter Notebooks (.ipynb) programmatically, multi-line triple-quoted code strings containing quotes or escapes can suffer string-interpolation stripping; parse every code cell string with `ast.parse()` to catch syntax breaks before writing.
- For shareable Google Colab deliverables, bypass browser 2FA and login barriers by pushing the notebook to a public GitHub repo via `gh repo create --public` and providing the native URL `https://colab.research.google.com/github/<user>/<repo>/blob/main/<notebook>.ipynb`.
